[1] 프로젝트 개요
------------------------------------------------------------
AI 코딩 에이전트가 대화 도중 특정 시점에서 다음에 취할 행동(action)을
14개 클래스 중 하나로 예측하는 문제.

데이터: train.jsonl(70,000건) + train_labels.csv
평가: macro F1

14개 클래스:
  read_file, grep_search, list_directory, glob_pattern,
  edit_file, write_file, apply_patch,
  run_bash, run_tests, lint_or_typecheck,
  ask_user, plan_task, web_search, respond_only


[2] 원본(초기) 코드 상태
------------------------------------------------------------
초기 코드는 아래 두 부분만 존재했음.

1) 데이터 로드
   - train.jsonl, train_labels.csv를 읽어 X(current_prompt), y(action) 구성

2) 모델 정의 및 학습
   - TfidfVectorizer 1개 (단어 단위, ngram_range=(1,2), min_df=2,
     max_features=80000, sublinear_tf=True)
   - LogisticRegression (max_iter=500, class_weight='balanced', C=2.0)
   - pipe.fit(X_train, y_train) 까지만 존재
   - train/test 분할 코드, 평가 코드, 모델 저장 코드 없음


[3] 변경 사항 및 사유 (초기 코드 -> 현재 코드)
------------------------------------------------------------

--------------------------------------------------------------
3-1. 벡터화: 단어 TF-IDF 단일 -> 단어+문자 TF-IDF 병행 (FeatureUnion)
--------------------------------------------------------------
변경 전: TfidfVectorizer(ngram_range=(1,2), max_features=80000) 1개
변경 후: 아래 2개를 FeatureUnion으로 결합
  - word: ngram_range=(1,2), max_features=60000  (기존과 동일 계열)
  - char: analyzer='char_wb', ngram_range=(2,4), max_features=20000  (신규)

사유:
  - 데이터 언어 비중 확인 결과: 한국어 64.33% / 영어 25.43% / 혼합 10.24%
    (session_meta.language_pref 기준, 전체 70,000건)
  - 혼합 문장(예: "refund 좀 해줘")은 단어 단위 토큰화만으로는
    희소한 패턴이 되어 학습이 불안정할 수 있음
  - 문자 단위(char n-gram)는 언어 경계에 무관하게 동작하여
    혼합 문장에 대한 강건성을 보완하기 위해 추가
  - max_features를 word/char에 나눠 배분(60000/20000)하여
    문자 단위 토큰이 어휘 예산을 과도하게 잠식하지 않도록 제한

주의(미검증 상태):
  - char n-gram 범위(2~4)와 예산 배분(60000/20000) 비율은
    실험적으로 결정된 값이 아니라 초기 가정값임
  - 언어별 F1(아래 3-4 참고)을 통해 실제 효과 검증 필요


--------------------------------------------------------------
3-2. 분류기: LogisticRegression -> LGBMClassifier (LightGBM)
--------------------------------------------------------------
변경 전: LogisticRegression(max_iter=500, class_weight='balanced', C=2.0)
변경 후: LGBMClassifier(
           objective='multiclass', num_leaves=63, learning_rate=0.05,
           n_estimators=500, min_child_samples=20,
           class_weight='balanced', random_state=42, n_jobs=-1)

사유:
  - 프로젝트 진행 계획 문서(스크린샷)상 [stage1] 1.1.2 항목이
    "LightGBM 분류기 학습"으로 명시되어 있어 해당 계획을 따름
  - LogisticRegression -> LightGBM은 선형 모델 -> 트리 기반 모델로
    알고리즘 자체가 다름 (성능 비교 데이터 없음, 계획 문서 기준 반영)

주의(미검증 상태):
  - num_leaves, learning_rate, n_estimators, min_child_samples는
    "고차원 희소 TF-IDF + 다중클래스" 상황에서 일반적으로 무난하다고
    알려진 값을 그대로 넣은 것으로, 하이퍼파라미터 튜닝은
    수행되지 않았음 (GridSearch/RandomSearch/Optuna 등 미적용)
  - LogisticRegression 대비 실제 성능이 더 나은지 여부는
    아직 비교 실험을 하지 않았음


--------------------------------------------------------------
3-3. train/test 분할 로직 명시적 추가
--------------------------------------------------------------
변경 전: 없음 (X_train, y_train이 어떻게 만들어졌는지 코드에 없었음)
변경 후:
  train_test_split(X, y, lang, test_size=0.2, random_state=42, stratify=y)

사유:
  - 14개 클래스 간 분포 불균형을 고려해 stratify=y 적용
  - random_state 고정으로 재현성 확보
  - 아래 3-4 평가를 위해 lang(언어 라벨)도 X, y와 함께 분할


--------------------------------------------------------------
3-4. 평가 로직 추가 (전체 F1 + 언어별 F1)
--------------------------------------------------------------
변경 전: 없음 (print("학습 완료")까지만 존재)
변경 후:
  - f1_score(y_test, y_pred, average='macro') 로 전체 macro F1 산출
  - classification_report로 클래스별 precision/recall/F1 확인
  - session_meta.language_pref(ko/en/mixed) 기준으로 그룹별
    macro F1을 별도 산출

사유:
  - 모델의 실질적 성능을 확인할 수단이 전무했음
  - 혼합 문장(10.24%)이 상대적으로 데이터가 적어, 전체 F1만으로는
    이 그룹의 성능 저하를 놓칠 수 있어 언어별로 분리 확인
  - language_pref는 세션 메타데이터에 이미 제공되는 필드이므로
    별도의 언어 감지/추정 로직 없이 그대로 사용
  - 단, 이 필드는 모델의 입력(X)으로는 사용하지 않음 — 평가 전용


--------------------------------------------------------------
3-5. 모델/테스트셋 저장 로직 추가
--------------------------------------------------------------
변경 전: 없음
변경 후:
  joblib.dump(pipe, './model/tfidf_lgbm.pkl')
  joblib.dump({'X_test':X_test, 'y_test':y_test, 'lang_test':lang_test},
              './model/test_set.pkl')

사유:
  - 학습 결과물을 재사용 가능한 형태로 남겨야 추론 스크립트,
    추후 예정된 경량화(ONNX 변환+양자화) 작업에서 이어받을 수 있음
  - test_set.pkl은 향후 경량화 전/후 F1을 동일 기준으로
    재측정하기 위한 목적으로 별도 저장


--------------------------------------------------------------
3-6. 추론 스크립트(script.py) 모델 경로 수정
--------------------------------------------------------------
변경 전: MODEL_PATH = os.path.join(MODEL_DIR, "tfidf_logreg.pkl")
변경 후: MODEL_PATH = os.path.join(MODEL_DIR, "tfidf_lgbm.pkl")

사유:
  - 3-2에서 분류기를 LogisticRegression -> LightGBM으로 교체하면서
    학습 스크립트의 저장 파일명도 tfidf_logreg.pkl -> tfidf_lgbm.pkl로
    함께 바뀌었음
  - 추론 스크립트(script.py)는 원래 tfidf_logreg.pkl을 그대로
    참조하고 있어서, 수정하지 않으면 새로 학습한 LightGBM 모델이
    아니라 예전 로지스틱 회귀 모델을 계속 불러오게 되는 문제가 있었음
  - 추론 로직(load_jsonl, extract_text, merge_predictions 등)은
    전혀 손대지 않았고, MODEL_PATH 한 줄만 수정

주의:
  - model/ 폴더에 예전 tfidf_logreg.pkl이 남아있어도 추론 스크립트가
    더 이상 참조하지 않으므로 동작에는 문제없음. 다만 혼동 방지를
    위해 삭제하거나 tfidf_logreg_deprecated.pkl처럼 이름을 구분해
    보관하는 것을 권장
  - 만약 향후 다시 LogisticRegression으로 되돌리거나 두 모델을
    비교 실험하는 경우, MODEL_PATH를 실험 대상에 맞춰 다시
    변경해야 함 (현재는 하드코딩된 상수)


[4] 의도적으로 아직 반영하지 않은 것 (범위 밖)
------------------------------------------------------------
아래 항목은 "빠뜨린 것"이 아니라 "다음 단계로 의도적으로 미룬 것"임.

1) history 필드 미사용
   - 사유: current_prompt 단독 성능을 먼저 베이스라인으로 확보한 뒤,
     history를 추가했을 때 성능이 실제로 오르는지 비교 검증하기 위함
   - 향후 방향: 직전 assistant_action.name(직전 행동), 최근 N턴
     시퀀스 등을 별도 피처로 추출하여 FeatureUnion에 추가 예정

2) session_meta / workspace 구조화 정보 미사용
   - 대상 필드: user_tier, budget_tokens_remaining, turn_index,
     elapsed_session_sec, workspace.loc, workspace.git_dirty,
     workspace.last_ci_status, workspace.open_files,
     workspace.language_mix 등
   - 사유: 위 1)과 동일한 이유로 텍스트 단독 베이스라인을 먼저 확정
   - 향후 방향: DictVectorizer를 이용해 범주형/수치형 피처를
     텍스트 피처와 별도 브랜치로 결합 (설계 초안은 작업 중 논의됨,
     별도 코드 파일로 존재하지 않음 — 필요 시 재작성 필요)

3) 언어별 모델 완전 분리 미적용
   - 검토는 했으나, 혼합 문장(10.24%) 존재로 인해 "이 문장이
     어떤 언어인가"를 규칙 기반으로 나누는 것 자체가 애매한 경계를
     만들 수 있어, 우선 단일 파이프라인 + word/char 병행 전략을 채택
   - session_meta.language_pref로 언어가 이미 명시되어 있으므로,
     추후 완전 분리 전략을 시도할 경우 언어 감지 로직 없이
     이 필드를 기준으로 라우팅 가능

4) 하이퍼파라미터 튜닝 미적용 (3-2 참고)

5) 경량화(ONNX 변환 + 양자화) 미적용
   - Stage 1(TF-IDF+LightGBM)은 이미 가벼운 모델이라 우선순위 낮음
   - Stage 2(multilingual MiniLM 등 임베딩 기반 모델) 도입 시
     적용 예정. 별도 변환 스크립트 초안 논의됨(파일 미보관,
     필요 시 재작성 필요)

[6] 다음 담당자를 위한 제안 순서
------------------------------------------------------------
1. 현재 코드 그대로 실행해 베이스라인 macro F1(전체/언어별) 확보 및 기록
2. session_meta / workspace 구조화 피처를 DictVectorizer로 추가,
   FeatureUnion에 결합 -> F1 변화 확인 (구조화 피처 branch는
   별도로 새로 작성 필요, 4-2 항목 참고)
3. history에서 직전 action 등 파생 피처 추가 -> F1 변화 확인
4. 위 단계별로 F1이 실제로 개선되는지 확인 후 채택 여부 결정
5. LightGBM 하이퍼파라미터 튜닝 (Optuna 등) — 2~4단계 이후 진행 권장
   (피처 셋이 바뀔 때마다 최적 하이퍼파라미터도 달라지므로,
   피처 구성을 먼저 확정한 뒤 튜닝하는 것을 권장)
6. Stage 2(multilingual MiniLM) 검토 — 위 단계로도 성능 부족 시
7. Stage 2 도입 시에만 ONNX 변환 + INT8 양자화 적용,
   변환 전/후 F1을 언어별로 반드시 재확인
